# Источник конфигурации etcd для Community Edition

`tnt-ce-etcd` читает конфигурацию кластера из etcd и отдаёт её ядру
Tarantool Community Edition. Узлу говорят, где лежит конфигурация, тем же
разделом `config.etcd`, что и в Enterprise:

```yaml
config:
  etcd: {endpoints: ['http://127.0.0.1:2379'], prefix: /demo}
```

```sh
tt cluster publish http://127.0.0.1:2379/demo cluster.yaml
TNT_CE_EXTENSIONS=tnt.ce.etcd tarantool --name instance-001 --config config.yaml
```

Узел поднимается на конфигурации из etcd, сам замечает её правку, а при
лежащем etcd поднимается на снимке последней прочитанной и сам сходит
с него, когда etcd вернётся.

## Зачем пакет

Конфигурация кластера, разложенная файлами по машинам, расходится: каждую
правку топологии надо донести до каждого узла, и узел, до которого она
не дошла, живёт на старой. Общий источник правды — etcd: конфигурация
лежит в одном ключе, и узлы читают её оттуда. В Enterprise такой источник
встроен, а Community Edition раздел `config.etcd` отвергает:

```
[cluster_config] config.etcd: This configuration parameter is available only in Tarantool Enterprise Edition
```

Пакет — расширение `tnt-ce-extras`: тот открывает в схеме ровно раздел
`config.etcd` и регистрирует источник, а источник читает конфигурацию
по HTTP-шлюзу etcd API v3. Что он даёт сверх чтения:

- **Раздел — по схеме ядра.** Поля `config.etcd` читаются под теми же
  именами и с теми же значениями, что в Enterprise, а ключ вне схемы
  и раздел без `prefix` ядро по-прежнему отвергает. Конфигурация,
  написанная для этого источника, переезжает на Enterprise без правки.
- **Авария etcd не мешает перезапуску.** Встроенный источник делает etcd
  обязательным для старта. Здесь после каждого удачного чтения
  конфигурация ложится в локальный снимок, и узел, которому etcd
  не ответил, поднимается на нём и говорит, что конфигурация устарела.
  Откат выключается, если расхождение опаснее простоя.
- **Правку узел замечает сам.** Наблюдатель раз в пять секунд спрашивает
  ревизию ключа и, если она выросла, просит ядро перечитать конфигурацию.
  Узел на снимке так же замечает вернувшийся etcd, а узел, поднятый
  до первой записи конфигурации, — саму запись.
- **Прочитанное отличается от применённого.** Источник рассказывает ядру
  ревизию ключа, и ядро помнит отдельно прочитанную и применённую.
- **Перечитывание от узкой учётки.** Источник не трогает спейсов `box`,
  и перечитать конфигурацию может учётка с правом на одну функцию.

Зависимости: `tnt-ce-extras` (точка входа ядра, открытие `config.etcd`,
реестр источников), `tnt-env` (путь снимка и выключатель отката из
окружения и `.env`), `tnt-context` и `tnt-id` (своя область с новым
`request_id` на каждый заход наблюдения), `tnt-log` (журнал, который
прячет пароль в адресе), `tnt-must` (отказ без места в коде),
`tnt-external` (вопрос «настроен ли `box`» подменяется в проверках)
и `tnt-fs` (атомарная подмена снимка со сбросом на диск, его чтение
и время правки).

## Как пользоваться

### Подключение: `TNT_CE_EXTENSIONS`

Пакет ставится обычным роком, `tnt-ce-extras` приходит с ним
зависимостью. Источник заводится, когда модуль `tnt.ce.etcd` назван
в списке расширений — в окружении процесса или строкой в `.env` каталога
запуска:

```sh
TNT_CE_EXTENSIONS=tnt.ce.etcd tarantool --name instance-001 --config config.yaml
```

С другими расширениями — через запятую:
`TNT_CE_EXTENSIONS=tnt.ce.etcd,app.memory`. Список читает каркас,
однажды на процесс; правила списка и почему он берётся из каталога
запуска — в документе `tnt-ce-extras`.

Без расширения узел с `config.etcd` не поднимается: схема отвергает раздел
текстом выше. Установка пакета сама по себе ничего не меняет.

### Раздел `config.etcd`

Раздел пишут в файл узла — рядом с тем, что узлу нужно знать до etcd:

```yaml
config:
  etcd:
    endpoints: ['http://127.0.0.1:2379']
    prefix: /demo
    http:
      request:
        timeout: 2s
    watchers:
      reconnect_timeout: 1m
      reconnect_max_attempts: 3
```

| Поле | Что это |
|---|---|
| `endpoints` | адреса etcd, непустой список; перебираются по порядку |
| `prefix` | где лежит конфигурация: ключ `<prefix>/config/all` |
| `username`, `password` | вход в etcd; без имени вход не делается |
| `ssl.ca_file`, `ssl.ca_path` | доверенные центры для `https://` |
| `ssl.ssl_cert`, `ssl.ssl_key` | клиентский сертификат и его ключ |
| `ssl.verify_peer`, `ssl.verify_host` | проверять ли сертификат сервера и имя в нём |
| `http.request.timeout` | срок одного запроса; по умолчанию 5 с |
| `http.request.unix_socket`, `http.request.interface`, `http.request.verbose` | уходят в `http.client` как есть: сокет вместо сети, исходящий интерфейс, подробный вывод curl |
| `watchers.reconnect_timeout` | пауза наблюдения после неудачной попытки |
| `watchers.reconnect_max_attempts` | сколько неудач подряд наблюдение терпит |

Длительности записываются так же, как принимает ядро: числом секунд либо
строкой с единицей — `2s`, `1m`. Разбирает их само ядро, поэтому новая
единица, которую ядро однажды примет, годится и здесь.

Порядок источников задаёт ядро: окружение, файл, затем etcd, последним —
окружение с умолчаниями. Значение из файла главнее значения из etcd:
то, что должно приходить из хранилища, в файл не пишут.

Отказы раздела останавливают старт и перечитывание. Непустой список
адресов проверяет сам источник — схема ядра пустого списка
не отвергает; текст уходит оператору в выводе старта без приписки места
в коде:

```
[tnt.ce.etcd] config.etcd.endpoints должен быть непустым списком
```

Остальное проверяет схема ядра раньше, чем раздел дойдёт до источника, —
раздел без префикса, префикс без ведущей косой черты и чужое поле:

```
[cluster_config] config.etcd: No config.etcd.prefix provided
[cluster_config] config.etcd.prefix: config.etcd.prefix should be a path alike value, got "demo"
[cluster_config] config.etcd: Unexpected field "watch_interval"
```

Схема судит вывод каждого источника порознь, поэтому раздел пишут
целиком в одно место: `endpoints` в файле и `prefix` в окружении
(`TT_CONFIG_ETCD_PREFIX`) — такой же отказ о файле.

### Где лежит конфигурация

Основной ключ — `<prefix>/config/all`: туда её кладёт
`tt cluster publish`.

```sh
tt cluster publish http://127.0.0.1:2379/demo cluster.yaml
```

Значение ключа — YAML конфигурации кластера целиком: `credentials`,
`groups` и всё прочее. Хвостовые косые префикса отбрасываются: `/demo/`
и `/demo` читают один ключ.

Если основного ключа нет, читается старый — `<prefix>/config`. Его
оставили, чтобы развёртывания на нём обновляли пакет без разовой
миграции; Enterprise его не читает, и для переезда конфигурацию переносят
под основной ключ.

Нет ни того, ни другого — это не отказ, а пустая конфигурация: узел
поднимается из прочих источников, а журнал говорит, что читать нечего:

```
конфигурации в etcd нет, ключ пуст key=/demo/config/all
```

Записи журнала здесь и ниже — без даты и уровня: до `box.cfg` журнал
ядра ещё не настроен, и запись первого чтения уходит в stderr одной
строкой, а после — обычной записью с уровнем.

### Адреса, вход и шифрование

Адреса опрашиваются по порядку, по одной попытке на адрес, до первого
ответившего. Если не ответил ни один, отказ перечисляет каждый:

```
ни один адрес etcd не ответил:
  - http://10.255.255.1:2379: http://10.255.255.1:2379/v3/kv/range: HTTP 408:
  - http://127.0.0.1:1: http://127.0.0.1:1/v3/kv/range: HTTP 595:
```

Коды — `http.client`: 408 — вышел срок запроса, 595 — связи нет вовсе
(порт закрыт, имя не разрешилось). Ответ etcd с ошибкой назван своим
кодом и телом.

Ответ «ключа нет» от первого ответившего окончателен: остальные адреса —
тот же кластер etcd, и спрашивать их незачем.

С `username` источник перед каждым чтением берёт токен
(`/v3/auth/authenticate`) и отдаёт его с запросом. Токен не хранится:
etcd отзывает токены при смене учётных данных, и сбережённый отказал бы
в ту минуту, когда пароль сменили.

```yaml
config:
  etcd:
    endpoints: ['http://127.0.0.1:2379']
    prefix: /demo
    username: app
    password: secret
```

Раздел `ssl` действует только на адреса `https://`. Признаки проверки
уходят в `http.client` булевыми: незаданный — проверка включена,
`verify_peer: false` сам по себе имени в сертификате не отключает —
для этого есть `verify_host: false`. etcd, требующий клиентский
сертификат:

```yaml
config:
  etcd:
    endpoints: ['https://127.0.0.1:2379']
    prefix: /demo
    ssl:
      ca_file: ca.pem
      ssl_cert: client.pem
      ssl_key: client.key
```

Всякий отказ, кроме «ключа нет», — отказ связи: закрытый порт, срок
запроса, ответ 4xx и 5xx, неудачный вход, сорванное рукопожатие TLS.
Что за ним следует, решает откат на снимок.

### Откат на снимок

После каждого удачного чтения значение ключа ложится в снимок — по
умолчанию `var/etcd-config-snapshot.yaml` в рабочем каталоге узла. Запись
идёт подменой `fs.replace` из `tnt-fs`: во временный файл рядом —
скрытый, со случайной частью имени, — со сбросом на диск,
переименованием поверх снимка и сбросом каталога. Обрыв посреди записи
не оставит обрезанного снимка, отключение питания — пустого, а два
сохранения разом не пишут в один временный файл. Неудачная запись узел
не роняет: снимок — подстраховка, а не источник правды, и журнал говорит
о ней предупреждением `снимок конфигурации не сохранён` с причиной:

```
снимок конфигурации не сохранён err="не удалось записать var/etcd-config-snapshot.yaml: No space left on device"
```

Если etcd не ответил, узел поднимается на снимке и пишет предупреждение:

```
etcd недоступен, инстанс поднимается на снимке reason="ни один адрес etcd не ответил:…" snapshot=var/etcd-config-snapshot.yaml
```

Такой узел в состоянии источника помечен `stale = true`, ревизии у него
нет, а время чтения — время правки снимка. Правило диагностики
`config_revision` из `tnt-ce-extras` находит его отдельной находкой.
Наблюдение у него идёт: как только etcd ответит, узел сам перечитает
конфигурацию и сойдёт со снимка — за один такт, без ручного
`config:reload()`.

Старт на снимке невозможен в трёх случаях, и каждый — отказ со своим
текстом:

```
[tnt.ce.etcd] etcd недоступен, откат на снимок выключен: <причина>
[tnt.ce.etcd] etcd недоступен и снимка нет, стартовать не на чем.
[tnt.ce.etcd] снимок повреждён: конфигурация из etcd не разобрана как YAML: …
```

Во втором случае за первой строкой идут причина отказа etcd и
`снимок var/etcd-config-snapshot.yaml не найден`.

### Окружение: `TNT_CE_ETCD_SNAPSHOT` и `TNT_CE_ETCD_FALLBACK`

| Переменная | Что это | По умолчанию |
|---|---|---|
| `TNT_CE_ETCD_SNAPSHOT` | путь снимка; относительный — от рабочего каталога узла | `var/etcd-config-snapshot.yaml` |
| `TNT_CE_ETCD_FALLBACK` | разрешён ли откат на снимок | разрешён |

Обе читает `tnt-env`: переменная процесса главнее строки в `.env`,
а выключатель — логическое по общему правилу: `off`, `false`, `0`, `no`
выключают откат, `on`, `true`, `1`, `yes` оставляют. Прочее — отказ,
и пустое значение тоже:

```
переменная окружения TNT_CE_ETCD_FALLBACK — логическое значение (true, false, 1, 0, yes, no, on, off), а не «»
```

Пустой путь снимка, напротив, — умолчание. Разница нарочная: снимок без
имени файла записать некуда, и пустоту оставляют, когда хотят умолчания,
а пустой выключатель — решение, которое оператор начал записывать и
не записал; откат, включённый за него, — та самая ошибка, от которой
бережёт отказ.

Окружение читается одним прочтением в начале каждого чтения
конфигурации, ещё до похода в etcd. Опечатка в выключателе останавливает
старт сразу, а не в тот час, когда etcd лёг и откат нужнее всего. Путь,
по которому снимок ищут, пишут и называют в журнале, берётся из одного
прочтения и разойтись не может. Правка `.env` действует со следующего
чтения — с ближайшего `config:reload()`.

### Каталог узла: `process.work_dir`

`.env` источника и относительный путь снимка считаются от рабочего
каталога узла — по правилу, по которому ядро само читает файлы при сборе
конфигурации. Ядро зовёт источник по обе стороны `box.cfg`: на старте,
ещё раз сразу после `box.cfg`, если подъём мог быть долгим (у узла
с данными — на всяком перезапуске), и на каждом `config:reload()`. После
первого `box.cfg` процесс уже стоит в рабочем каталоге, а до него каталог
приписывается руками. Без этого правила первое чтение брало бы `.env`
каталога запуска, а следующие — рабочего, и выключатель, сказанный только
рабочему каталогу, пропускал бы первый старт и ронял перезапуск.

Узел с такой конфигурацией берёт `.env` источника из
`nodes/instance-001/.env`, и относительный путь снимка из него считается
оттуда же:

```yaml
process:
  work_dir: 'nodes/{{ instance_name }}'
```

Отсюда, куда что класть: `TNT_CE_EXTENSIONS` — в `.env` каталога
запуска, его читает каркас однажды и раньше всех; `TNT_CE_ETCD_SNAPSHOT`
и `TNT_CE_ETCD_FALLBACK` — в `.env` рабочего каталога.

До `box.cfg` каталог берётся из того, что собрали источники до etcd, —
окружения (`TT_PROCESS_WORK_DIR`) и файла. Из подстановок раскрывается
одна — `{{ instance_name }}`: имя инстанса ядро знает с запуска. Каталог
с `{{ replicaset_name }}` и прочими подстановками до чтения etcd
не определить; узел тогда не падает, а читает каталог запуска и говорит
почему предупреждением:

```
каталог узла не определён: .env и снимок считаются от текущего err="process.work_dir «w-{{ replicaset_name }}»: до box.cfg раскрывается только {{ instance_name }}"
```

### Наблюдение за ключом

Всякое чтение конфигурации, кроме отказа, заводит наблюдателя — фибер,
который раз в пять секунд спрашивает хранилище, с какого ключа чтение
взяло бы конфигурацию сейчас: основной ключ, а если его нет — старый.
Порядок тот же, что у самого чтения, и наблюдение видит ровно то, что
принесло бы перечитывание. Изменением считается:

- выросшая ревизия ключа, с которого прочитана конфигурация, — основного
  или старого;
- ключ, который теперь читается, у узла на снимке или без ключа: etcd
  вернулся либо конфигурацию записали впервые;
- другой ключ: основной записали поверх старого.

Заметив изменение, источник пишет в журнал и просит ядро перечитать
конфигурацию, а применяет её ядро, снова позвав источник. Решает, какая
конфигурация действует, одно место — ядро.

```
конфигурация в хранилище изменилась, перечитываю request_id=01M38KP57MJN0W8H5CNE3M61BQ
```

Сравнивается ревизия ключа, а не всего хранилища: ту двигает любая
запись в etcd — назначение лидера, замок, чужой ключ рядом, — и узел
перечитывал бы конфигурацию на каждую такую запись. Пропавший ключ
изменением не считается: перечитывание дало бы узлу пустую конфигурацию
вместо рабочей, и он живёт на той, что есть, — как при молчании
хранилища.

Молчание хранилища наблюдатель переживает по настройкам
`config.etcd.watchers`: после неудачной попытки ждёт `reconnect_timeout`
(без него — обычные пять секунд), а после `reconnect_max_attempts` неудач
подряд останавливается и говорит об этом ошибкой в журнале:

```
наблюдение за конфигурацией остановлено: хранилище не отвечает attempts=3 err="…"
```

Без предела попытки не кончаются. Предел действует и на узле на снимке:
поставивший его выбрал громкую остановку вместо опроса без конца.
Остановленное наблюдение заводит заново следующее чтение, не кончившееся
отказом, — ближайший `config:reload()`, в том числе на снимке. Неудачное
перечитывание (`конфигурация не перечитана`) и бросок внутри захода
(`наблюдение за конфигурацией сорвалось`) наблюдателя не останавливают:
следующая правка может всё исправить. Так же переживается перечитывание,
о котором наблюдатель попросил, пока узел ещё поднимается: ядро его
отвергает (`instance configuration is already in progress`), прочитанное
источником не меняется, и следующий такт просит снова.

### Ревизия и состояние

Прочитав конфигурацию, источник рассказывает ядру ревизию ключа
(`config:_meta`). Ядро помнит её под именем источника: прочитанную —
в `meta.last`, применённую — в `meta.active`, и вторую переписывает
только после удачного применения:

```lua
config:info('v2').meta
--> { last = { etcd = { revision = 3 } }, active = { etcd = { revision = 3 } } }
```

Что источник говорит о себе, видно через каркас:

```lua
require('tnt.ce.extras').status().sources.etcd
--> { ready = true, stale = false, watching = true, revision = 3,
-->   endpoint = 'http://127.0.0.1:2379', synced_at = 1790216786.48 }
```

| Поле | Что это |
|---|---|
| `ready` | конфигурация прочитана — из etcd, снимка или пустая |
| `stale` | взята из снимка |
| `watching` | идёт ли наблюдение |
| `revision` | ревизия прочитанного ключа; на снимке и без ключа — нет |
| `endpoint` | адрес, который ответил |
| `synced_at` | когда прочитали, по стенным часам; на снимке — время его правки |

### Права и контекст

`sync` ядро зовёт в фибере того, кто читает конфигурацию, и от его учётки:
при старте это `admin`, при перечитывании — вызывающий. Источник поэтому
обходится без спейсов `box`: узкой учётке они закрыты, и чтение из них
уронило бы перечитывание оператора. Наблюдатель, рождённый таким вызовом,
живёт от `admin`: наблюдение — работа узла и обязано пережить вызов.

Наблюдатель порождается без контекста того, кто его завёл: иначе все его
заходы до перезапуска узла писались бы под опознавателем давно
закончившегося перечитывания. Каждый заход идёт в своей области
`tnt-context` с новым `request_id`: запись захода, перечитывание, которое
он попросил, и записи ролей, применённых этим перечитыванием, связаны
одним опознавателем, а соседние заходы — нет.

### Модули по отдельности

`require('tnt.ce.etcd')` регистрирует расширение и отдаёт три модуля:
`source`, `client` и `snapshot`. Наблюдение живёт в своём модуле
`tnt.ce.etcd.watch`, но оно — часть источника: работает над его
состоянием и заводится его `watch()`, отдельно его не зовут.

Клиент годится и сам по себе — например, чтобы прочитать ключ
из сценария; его берут напрямую, мимо точки подключения:

```lua
local client = require('tnt.ce.etcd.client').new({ timeout = 2 })

local body, err, meta = client:fetch({ 'http://127.0.0.1:2379' }, '/demo/config/all', {
    username = 'app',
    password = 'secret',
})
--> body — YAML конфигурации, err — nil,
--> meta — { endpoint = 'http://127.0.0.1:2379', revision = 7, mod_revision = 3 }
```

Отказ — пара `nil, err`; ключа нет — `nil`, причина и `meta.missing = true`.
В `meta.revision` — ревизия хранилища в миг ответа, только для отчёта,
в `meta.mod_revision` — ревизия ключа. Кроме `fetch`, у клиента есть
`request(endpoint, path, body, options)` — запрос к одному адресу
с разобранным JSON в ответе — и `authenticate(endpoint, username,
password, options)`.

Снимок:

```lua
local snapshot = require('tnt.ce.etcd.snapshot')

snapshot.settings('/srv/tarantool/instance-001')
--> { path = '/srv/tarantool/instance-001/var/etcd-config-snapshot.yaml', fallback = true }

local path = 'var/etcd-config-snapshot.yaml'
snapshot.save('app: {cfg: {greeting: привет}}\n', path)  --> true
snapshot.load(path)                                        --> 'app: {cfg: {greeting: привет}}\n'
snapshot.saved_at(path)                                    --> время правки, целые секунды

-- До box.cfg; после него — nil: путь считается от текущего каталога.
snapshot.directory({ process = { work_dir = 'w-{{ instance_name }}' } }, 'instance-001')
--> 'w-instance-001'
```

`save` и `load` отказывают парой `false, err` и `nil, err`: что
не удалось, называет снимок, почему — система.

```lua
snapshot.save('x: 1', '/etc/passwd/snapshot.yaml')
--> false, 'не удалось создать каталог /etc/passwd: File exists'
snapshot.load('/var/lib/none.yaml')
--> nil, 'снимок /var/lib/none.yaml не найден'
```

`saved_at` у снимка, которого нет или не опросить, отдаёт `nil`, а не
ноль: ноль читался бы как 1970 год.

### Подмена в проверках

Клиент, журнал, фибер наблюдателя, ожидание и перечитывание приходят
источнику аргументами `source.new`:

```lua
local source = require('tnt.ce.etcd.source').new({
    client_factory = function(opts) return fake_client end, -- вместо клиента etcd
    logger = fake_logger,       -- warn, info, error
    watch_interval = false,     -- без наблюдателя; число — свой такт в секундах
    reload = function() end,    -- вместо config:reload()
    spawn = function(body) end, -- вместо fiber.create
    sleep = function() end,     -- вместо fiber.sleep
})

source:sync(nil, { config = { etcd = { endpoints = { 'http://etcd:2379' }, prefix = '/demo' } } })
source:get()      --> прочитанная конфигурация
source:status()   --> { ready = true, stale = false, revision = 3, … }
```

Двойник клиента отвечает на `fetch(endpoints, key, options)` тремя
значениями, как настоящий. Транспорт клиента подменяется так же:
`client.new({ http_client = fake })`, где у `fake` есть
`request(self, method, url, body, options)`. Файлы снимок читает
и пишет через `tnt-fs`, и отказ диска подменяется там, в `fio` фасада;
довольно назвать одно действие, остальное взять у настоящего `fio`:

```lua
require('tnt.fs')._set_source({
    fio = setmetatable({ rename = refuse }, { __index = require('fio') }),
})
```

Вопрос «настроен ли `box`» —
`snapshot._set_source({ configured = function() return false end })`,
а окружение — у `tnt-env` (`_set_source`).

## Чем пришлось поступиться

**Только Community Edition.** В Enterprise источник встроен, а каркас
`tnt-ce-extras` там загружаться отказывается.

**Договор ядра — внутренний.** Регистрация источника, `config:_meta`,
`config._instance_name` и разбор длительностей
(`internal.config.utils.units`) — внутренности Tarantool, и между
версиями они вправе меняться. Опора — проверки на 3.8. На ядре без
`config:_meta` источник о ревизии просто молчит.

**Один ключ, а не ветка.** Enterprise читает всю ветку `<prefix>/config/`
и сливает значения её ключей; здесь читается один ключ — тот, что пишет
`tt cluster publish`. На переезде разница не сказывается, пока в ветке
нет ничего, кроме конфигурации: своё рядом держат вне её, например
историю правок — в `<prefix>/history/`, иначе Enterprise слил бы это
в конфигурацию и отверг как неизвестные поля.

**Ревизия ключа, а не хранилища.** Встроенный источник Enterprise кладёт
под `revision` ревизию хранилища. Здесь номер один — ревизия ключа:
по нему судят, одну ли конфигурацию применили узлы, а ревизия хранилища
развела бы узлы, прочитавшие одну конфигурацию в разные мгновения.

**Наблюдение — опросом раз в пять секунд.** Поток `/v3/watch` источнику
ничего не дал бы: раскатка и так просит узлы перечитать конфигурацию
сразу после записи, а правку руками несколько секунд задержки не портят.
Такт настройкой не меняется: схема ядра поля для него не знает,
а своё поле ядро отвергло бы.

**Старый ключ стоит такту двух чтений.** Наблюдение спрашивает ключи
в том же порядке, что и чтение, и развёртывание на старом ключе
`<prefix>/config` платит за такт двумя чтениями: основного ключа,
которого нет, и старого. Зато переезд на основной ключ узел замечает сам.

**Токен — на каждое чтение.** С `username` каждое чтение ключа —
и в `sync`, и в такте наблюдения — два запроса: вход и чтение. Зато
токен, отозванный сменой пароля, не ломает узел.

**Всякий отказ etcd — повод для отката.** Неверный пароль и чужой
сертификат узел переживает так же, как лежащий etcd: поднимается на
снимке, если тот есть. Отличить «хранилище не пускает» от «хранилища нет»
можно по причине в журнале и по `stale` в состоянии, а кластеру, где
это опаснее простоя, откат выключают.

**Снимок — копия конфигурации как есть.** В нём лежит всё, что лежит
в ключе, в том числе пароли раздела `credentials`. Файл создаётся
с правами `0644` за вычетом umask процесса: каталог снимка закрывают
правами самого каталога.

**Отказы — исключения.** Источник зовёт ядро, и отказ источника значит
«конфигурации нет»: пару `nil, err` ядру вернуть некуда. Отказ бросается
без места в коде — его читает оператор.

## Проверки

Проверки лежат в `test/` и идут на luatest. Ни etcd, ни сеть не нужны:
у клиента транспорт — двойник с заготовленными ответами, у источника —
двойник клиента, снимок уходит во временный каталог, наблюдатель не
запускается фибером — проверка сама решает, когда сделать такт. Снимок
проверяется на настоящих файлах, ветки отказа записи — кончилось место,
не сбросился файл, не переименовался — подменой `fio` у `tnt-fs`,
окружение и `.env` — подменой `tnt-env`, в которой задано ровно то, что
нужно проверке.

Две живые проверки поднимают настоящий узел 3.8: только настоящее ядро
зовёт источник по обе стороны `box.cfg` и исполняет перечитывание,
о котором просит наблюдатель. `work_dir_live_test.lua` — узел
с `process.work_dir`, отличным от каталога запуска; etcd в ней нет
нарочно — адрес указывает на закрытый порт, и узел поднимается на снимке.
`watch_live_test.lua` — узел, поднятый на снимке при молчащем etcd:
на его адресе после старта заговаривает двойник HTTP-шлюза etcd
на сокете проверки, и узел сам сходит со снимка за один такт наблюдения.

Покрытие строк — 100 %, убитых мутантов — 100 %.
